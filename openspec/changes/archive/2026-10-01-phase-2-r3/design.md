# Design: phase-2-r3

> 本轮的核心不是「做了哪些效果」，而是**四次归因错误的更正记录**。效果本身的做法在代码注释里
> 已经写得很细，这里只留**决策与教训**，尤其是那些花了多轮才收敛的部分 —— 它们比结果更值得留档。

## D1 · 天体：移植参照组件的「球」，而不是自己画一个「圆片」

参照组件那颗球的观感**不是**由径向渐变产生的，而是由六条 `box-shadow` 产生的：

```
-0.02em 0 0.032em  <limb>      inset   右侧冷色受光边缘
 0.06em 0.008em 0.1em  <ao-strong> inset   晨昏线内侧的强暗部
-0.096em -0.008em 0.136em <limb-soft> inset  更宽的柔光环
 1em     0    0.176em <ao-far>  inset   大偏移的远侧暗部
 0.6em   0    0.152em <ao-mid>  inset   中等偏移的暗部
```

我第一版用三条径向渐变近似，结果**弱了一个数量级** —— 看起来是一枚灰色圆片，不是一个被侧光照亮的球。
改正的做法是**逐条移植**，并把 `px` 基准换成 `em`（base = 直径），这样球缩放时明暗跟着缩放。

**三条实现纪律**：
1. `inset` 的 `box-shadow` **画在内容之下** —— 所以明暗必须放在**贴图之上的独立覆层**（`.shade`），
   而不是贴图自己身上。`outset` 的那条留在 `.sphere` 上（覆层在裁剪窗口内部，不会漏出去）。
2. **七颗星必须放在圆形裁剪窗口之外**。参照组件的七颗星坐标全部落在它自己那个 `overflow: hidden`
   的 250px 圆里 → 一颗都看不见（用 `elementFromPoint` 实测 0/7）。我们的做法是把 `.stars`
   做成 `.sphere` 的**兄弟节点**。
3. 月球的亮度踩过一次坑：初版用不透明底色 + `stop-opacity: 1`，结果是**一个纯白圆盘盖住正文**。
   修法是把透明度写进颜色本身（`rgb(232 234 242 / 15%)`），而不是靠 `opacity` 叠加。

## D2 · 分节停靠：用「视口中线一条窄带」，不用「21 档 threshold 取最大可见比例」

参照组件用 `scroll` 监听算「离视口中心最近的一节」。本站全站只有一个滚动监听
（`useScrollProgress`，它写 `--scroll-p`），所以这里改用 `IntersectionObserver` —— 与 `useReveal` 同一套机制。

第一版用 **21 档 threshold**（0 / 0.05 / … / 1）观察 7 个区块，逻辑上更严谨（能正确处理高度差很大的区块），
但每个渲染帧都要重算 7 个目标的交点比例并与 21 档逐一比较。改成
`rootMargin: '-45% 0px -45% 0px'` + 单档 threshold 之后，只有「跨过视口中线」这一个事件会触发回调，
全程约 14 次；高度不同的区块同样能正确处理，因为带子只有 10% 高，任何时刻最多一两个区块压在它上面。

> **但这条改动当时是被一个假信号推动的** —— 见 D7。

## D3 · 只用参照组件的两个想法，其余按本站令牌重做

参照组件是 **Next.js + framer-motion + Tailwind + shadcn** 的深色玻璃卡片。它**不能直接粘贴**：
7 个 TS 错误（`TS6133` ×5 未使用变量、`TS2694` `NodeJS.Timeout`、`TS2322` `sectionRefs` 类型不符），
Tailwind / shadcn 的类名在这里全部解析为空。

取的两个想法：
- **芯片化**（每个技术一枚独立胶囊）—— 这是它真正解决「乱」的地方；
- **指针聚光** —— 本站**已经有** `useSpotlight`（项目表格行在用），直接复用，**不引入 framer-motion**。

弃掉的：玻璃卡片本体（改成本站既有的 `.panel`）、`next/image` + 背景大图 + `blur(3xl)`
（一个 Next 专属组件 + 一次远程图片请求 + 一层全尺寸高斯模糊）。

**新增依赖只有一个 `lucide-react`**（实习经历切换条上的箭头 / 图标）。

## D4 · 技术栈换了 5 版：前 4 版都在同一族排法里换参数

| 版本 | 形态 | 用户反馈 |
| --- | --- | --- |
| r1 | 三列「名称 — 右侧等宽标签」规格表 | 太普通 |
| r2 | 「技能名 + 紧跟一个小灰字档位」连排 | 乱乱的 |
| r3-a | 大胶囊云（34px 胶囊 + 顶部图例） | 效果不行 |
| r3-b | 紧凑胶囊 / 三列对齐网格 / 组名在上两列（三选，出图给用户挑） | 都不行 |
| r3-c | **玻璃面板 + 分类色胶囊** | **采纳** |

**归因**：「乱」的来源被逐条数出来过 —— r2 有 **28 个档位小灰字**（28 条里 17 条是同一个「熟悉」）、
技能之间没有分隔符、每组技能数不同导致换行位置随机。

但真正的转折是用户那句 **「不要有这种背景是方块的」**：它一句话否掉了 r3-b 三个候选里的两个，
也点明了我一直在砍的东西正是用户要的 —— **容器**与**颜色**。前四版我砍掉它们的理由都"正当"
（spec 说面板只给两类区块；纪律说颜色只承担语义），但**当用户连续否定同一类输出时，
该质疑的是被自己当成前提的那条纪律，而不是继续在纪律内部换参数**。这一步我花了四轮才做到。

## D5 · 两个维度必须走两个正交通道

技术栈要同时表达「属于哪个方向」与「熟练到什么程度」。若两个维度挤在一个通道上
（例如都用颜色深浅），就会出现「蓝色深 = 熟悉」还是「蓝色 = 语言」的歧义。

**分类给色相、档位给填充深浅**，两者正交。代价是「深浅」这一通道**不能自明** ——
所以面板顶部那行三档图例是**硬要求**，不是装饰；而且**三档样片都必须可见**，
这条要求直接暴露了两次设计错误：

1. 第一版把「了解」做成「无填充 + 无描边」→ 图例里那一档**完全看不见**；
2. 第二版给它 5% 中性填充 → 又反过来**比「掌握」的 1px 描边更重**，层级颠倒。

最终是三档**单调阶梯**：填充与描边一起递减，三档共用同一副骨架（同样的圆角、内边距、字号）。
六个色相全部**避开状态色**（绿 / 黄 / 红）—— 那三个色相在本站专用于成功 / 警告 / 危险。

## D6 · 联系我：「端正」的来源是处处对齐，不是配色

用户反馈「太端正」。前两轮我按「换个组件」的思路做了三个方向（卡片网格 / 号码当标题四列 / 胶囊带），
回复是「都不好看，不要有这种背景是方块的」。

**重新归因**：端正不是配色问题，是**对称与一致**问题 —— r2 的四个次级入口全部左对齐在同一列、
等高 44px、每条压一条发丝线；完全一致的列宽与行高读起来就是一张表单。

最终方案（三条可判定的形式约束）：撤掉全部方块与发丝线；**标签内联写在值前面、不设固定列宽**
（值因此不再对齐在同一条竖线上）；号码移到左半、入口堆在右半（用满正文栏，那里原本是空的）。

## D7 · 一次被噪声驱动的返工（测量纪律）

加完分节停靠后，`audit-perf.cjs` 的 A 档报 **60–83% 掉帧**（此前 8–17%），我据此认定「滑动引入回归」，
接着做了一连串 A/B —— 结论互相矛盾：

| 试的改动 | A 档读数 |
| --- | --- |
| 卸载整个天体层 | 13–19% |
| 关掉 5 条内阴影 | 71% |
| 去掉 `will-change` | 63% |
| 换掉 `IntersectionObserver` | 63% |
| hook 空转 | 57% |
| 硬编码 scene 0 | 12% |

互相矛盾就说明**测的不是代码**。查下去发现：**同一份构建连跑四次的读数是 60% / 67% / 33% / 13%**。
A 档测的是「`load` 之后**不等待**、直接采样 3 秒」，这 3 秒里含字体子集加载、贴图解码、React 挂载，
全部被 IO 调度主导。

换成「等 2.5 秒让加载期落定再采样」的窗口复测：挂天体 **57.3 / 60.1 / 60.2 FPS（掉帧 1.2% / 0% / 0%）**，
不挂天体 **60.1 / 60.2 / 60.3 FPS（掉帧全 0%）**。**没有回归**。

**处置**：把这条使用边界写进 `audit-perf.cjs` 的文件头 —— 可靠用法是**同一构建内的相对比较**
（B 档很稳：58–60 FPS / 1%），A 档的绝对值**不能跨构建、跨改动比较**。

## D8 · 改版式会掀翻停靠表

联系我改成「号码左置 · 入口右列」之后，正文第一次**横跨整个正文栏**（368 → 1196），
而天体在 scene 6 原本停在**正中**（那时中间是空的）—— 实测球正好压在手机号和「微信」那一行上。

**做法不是凭感觉挪，是量**。用探针量出该停靠点下各块的矩形：

```
标题  84..1196 × 332..393
导语  84..344  × 417..447
正文  368..1196 × 417..597
页脚  0..1280  × 693..926
```

左侧唯一空出来的是 **y 447–693**（246px），于是把球（0.7 档 = 179px）放到这一段中线。

**而且这次「球压字」`audit-contrast` 是全绿的** —— 它量的是文字与**底色**的对比度，
不量「一个 0.24 不透明度的装饰层叠在文字下面」。所以这类问题只由 scene 0 的让位断言 + 肉眼截图把关。
**通用教训**：固定层 + vw/vh 停靠表与「随内容流动」的版式是一对耦合体，**改版式必须重新验停靠点**。

## D9 · 手机号上站：护栏收窄，而不是删除

`profile.test.ts` 原有一条 `手机号不出现在任何对外字段里`，来自 `decisions.md` #3「手机号默认不上站」
（公网个人站防骚扰），而 #3 当时就写了补救方式：「需要时在 `profileData.contacts` 加一项即可」。

用户明确要求上站，于是**收窄**为三条断言：① `contacts` 之外的任何字段都不许出现手机号；
② `contacts` 里恰好一条；③ 必须是 `tel:` 链接，且展示形态与拨号形态分别校验。
**防的是意外泄露，不是有意公开。**

## D10 · 判据要挂在稳定的标记上，不要挂在类名子串上

技术栈的验收探针原来写 `[class*="group"]`。这一版的类名是 `.group`（行）与 `.groupTitle`（行头）——
「groupTitle」里也含「group」，于是 `querySelectorAll` 把 6 行数成 **12 行**，断言当场亮红。

**处置**：给行加 `data-skill-group` 标记。这与 `data-award` / `data-year` / `data-photo` / `data-celestial`
是同一个套路：**类名是给样式的，标记是给判据的**，类名一改断言就跟着碎。

## D11 · 两条被审计抓到的实现缺陷

1. **聚光伪元素的横向出血撑破移动端**：`.wrap::before` 初版写 `inset: -1rem -1.5rem`（纵横都向外扩）。
   移动端容器左右各有 1rem 内边距，伪元素再向外 1.5rem ⇒ `16 − 24 = −8`，文档被撑到 398px。
   改成只做纵向出血。**装饰性的负 inset 是横向溢出的常客。**
2. **`white-space: nowrap` + 长名字撑破列**：768 那一档列宽只剩 189px，
   「操作系统 / I-O 多路复用」这类名字把文档横向撑出 **40px**（实测 `scrollWidth=808`）。
   名字必须允许在格内折行，窄屏那一档再单独加回 `nowrap`。

## D12 · 窄屏的降级：表格塌成「每个方向一块」

390 上四列硬挤会碎（行头 152px，剩 238px 分三列 = 每列 79px）。
`≤719px` 时把表格元素改成 `display: block`，方向名做小标题、三档纵向堆叠、档位名回到每一项前面。
这与全局 `.section { display: block }` 是同一套降级思路：**窄屏下让表格语义退场，可读性优先**。
代价是这一段的可访问性关联变弱（`display` 覆盖会让表格角色失效），已在 CSS 注释里写明。

## D13 · 一次白屏：JSX 注释插在了 map 回调的返回位置

给 `<div>` 加标记时，我把 `{/* … */}` 写在了 `groups.map((g) => (` 与返回的 `<div>` 之间 ——
箭头函数于是返回两个节点，TS 报 `TS1005`。构建失败 ⇒ 页面白屏 ⇒
**`audit-behavior` 22 条一起亮红**（所有探针都取不到节点）。

**教训**：断言大面积同时失败，先怀疑「页面根本没渲染」，而不是逐条去查 ——
白屏时每条探针都会给出一个看似合理的坏读数。
